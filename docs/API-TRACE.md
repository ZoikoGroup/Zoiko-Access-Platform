# External APIs and webhooks: the specification's 64 acceptance cases, checked against what is built

Written 2026-11-11 by the developer, from GHE-13 section 15. Each row is a judgement made by reading the case and the code, not an automatic result; "Met" means one of our own automated tests proves the behaviour. The specification's cases have **not** been run as written (they need partners, certificates, sandboxes and regions that do not exist). This is the developer's reading and nobody else has reviewed it.

**Totals: 13 met, 25 partly, 26 not built (of 64).**

What exists is outbound signed webhooks (DEV-127), partner credentials and signed inbound messages (DEV-131), request measurements (DEV-130) and country packs (DEV-128). The "not built" rows are mostly healthcare interoperability (FHIR, HL7, imaging), the published API documents and SDKs, OAuth, and the whole partner onboarding, sandbox and certification lifecycle, none of which can be built without a partner, a standards decision and an approver.

| Case | Group | What the specification tests | Status | Why, and where it is tested |
|---|---|---|---|---|
| T-01 | Contract and version | OpenAPI 3.1 definition validates and includes all live operations, security schemes, required schemas, errors and examples. | Partly | An OpenAPI 3.1 document is built from the live routes and served at /api/v1/openapi.json (test_openapi.py): every route, method, login requirement and the error shape. Request and response bodies are not described field by field, and there is no external validator run. |
| T-02 | Contract and version | AsyncAPI definition validates and matches approved event topic catalog and payload schema hashes. | Partly | An AsyncAPI 3.0 document of the 19 events (18 published, 1 sent straight to a partner) is built from a catalogue and served at /api/v1/asyncapi.json, each with a schema hash; a test fails if the code publishes an event the catalogue lacks or the reverse, and a checked-in snapshot shows any change (test_event_catalog.py). Payloads are listed by field name only; there is no approved topic review and no external validator. |
| T-03 | Contract and version | Backward-compatible additive change passes consumer-driven contract tests. | Partly | Every call the five apps make (routes and methods, taken from the apps' own source) is listed in api/consumer_contract.json and a test fails if the API stops serving one; adding routes passes (test_consumer_contract.py). Response fields are not checked, and no outside partner's contract is included. |
| T-04 | Contract and version | Breaking schema change without version bump blocks release. | Partly | A snapshot of the document is checked in and a test fails when the API changes without the snapshot being refreshed (test_openapi.py), so a change is visible in review. It does not tell a breaking change from an additive one and nothing blocks a release. |
| T-05 | Contract and version | Unsupported API major version returns documented safe response with deprecation guidance. | Partly | An unknown major version under /api/ gets the standard not-found body, the versions we serve and a link to v1 (test_api_versions.py); no deprecation schedule, as only v1 exists. |
| T-06 | Contract and version | Patient identifiers never appear in public or global API object IDs. | Met | Every public id column in the system (more than 50 tables) is filled only by the random generator and cannot be edited; the generator gave 2000 distinct 22-character ids; and after creating a patient with a distinctive identifier and login, no stored public id of that customer contains any part of it (test_public_ids.py). Partner messages and events carry only these ids. |
| T-07 | Contract and version | Cursor pagination cannot leak records when privilege is revoked between pages. | Partly | Lists can be read a page at a time with a signed cursor that holds only a position, belongs to one login and one list, and expires; every page checks the caller's rights again, so a right taken away between two pages stops the next page (test_pagination.py). The clinic's and the partner's request lists use it; other lists are still capped. |
| T-08 | Contract and version | OpenAPI examples and SDK fixtures contain no real patient data. | Met | The document carries no examples at all, so it holds no patient data (test_openapi.py). There is no SDK. |
| T-09 | Authentication and authorization | Interactive OAuth flow enforces PKCE and exact registered redirect URI. | Not built | No OAuth: partners use signed messages, not an interactive flow. |
| T-10 | Authentication and authorization | Machine client cannot use missing, expired, wrong-audience or wrong-region token. | Partly | test_partner_events.py: a missing, malformed, stale, future or wrong-key credential is refused. There are no audience or region claims. |
| T-11 | Authentication and authorization | Partner whose read scope exists but lacks relationship/purpose cannot fetch patient resources. | Not built | A partner cannot read patient resources at all, so there is no scope to check. |
| T-12 | Authentication and authorization | Partner cannot change tenant, patient ID, object property or region to escalate privileges. | Met | The customer comes from the key; bodies naming another tenant, cell or patient are held, not obeyed (test_partner_events.py). |
| T-13 | Authentication and authorization | Revoked certificate or client credentials block new calls immediately per revocation policy. | Met | test_partner_events.py: a suspended or revoked partner is refused at once. There are no certificates, only secrets. |
| T-14 | Authentication and authorization | Rotated signing keys validate across only the approved overlap interval. | Partly | test_partner_events.py, test_webhooks.py: a rotated secret ends the old one at once. There is no approved overlap interval. |
| T-15 | Authentication and authorization | Embedded SDK source and sample apps contain no long-lived production secret. | Not built | There is no SDK or sample app. |
| T-16 | Authentication and authorization | Cross-border API request is denied without explicit GHE-04/05 transfer authority. | Not built | No cross-border handling. |
| T-17 | Transport and webhook | Valid signed webhook is accepted once and issued a receipt reference. | Met | test_partner_events.py: a correctly signed message is accepted once and gets a receipt id. |
| T-18 | Transport and webhook | Tampered body is rejected before interpreting sender-provided clinical state. | Met | test_partner_events.py: a changed body fails the signature and nothing in it is read. |
| T-19 | Transport and webhook | Expired timestamp, missing nonce or reused nonce with changed digest is rejected. | Met | test_partner_events.py: a stale or future timestamp, a missing delivery id, and a reused id with different content are refused. |
| T-20 | Transport and webhook | Duplicate legitimate webhook has at most one domain business effect. | Partly | test_partner_events.py: a repeated delivery is stored once. No domain effect exists yet to count. |
| T-21 | Transport and webhook | Unverified destination, redirect or private-network URL cannot be registered for callbacks. | Met | test_webhooks.py: only public https addresses with no credentials or odd ports, a redirect is never followed (a local server answers 302 and the sender stops), and an address on a private network can never be verified or sent to. |
| T-22 | Transport and webhook | Timeout/5xx triggers bounded backoff with jitter and preserved delivery ID. | Met | test_webhooks.py: a server error is retried with growing, jittered waits and the same delivery id, then parked after 8 tries. |
| T-23 | Transport and webhook | DLQ entry after retry exhaustion retains owner, policy and evidence and is visible to authorized regional operator. | Met | test_webhooks.py: a delivery that gave up keeps its owner (who registered the address), the access rules in force when it was queued, a fingerprint of the exact message and its last answer, stays visible to the clinic administrator, is counted on their dashboard and can be sent again. |
| T-24 | Transport and webhook | Outbound 2xx transport receipt does not make CLINICAL_REVIEWED or HANDOFF_ACKNOWLEDGED true. | Met | test_webhooks.py: a webhook delivery never touches a workflow; test_orchestration.py refuses every transport receipt as evidence. |

| T-38 | Idempotency and consistency | Crash after local outbox commit delivers eventually without losing request or creating duplicate effects. | Partly | Webhook deliveries are rows in the database, so a crash does not lose them, and the outbox is at-least-once. | T-39 | Idempotency and consistency | Disconnect with pending pathway creates assigned human reconciliation task. | Partly | A request still open between a clinic and a partner when either customer is suspended is put on hold: the other side sees it, the partner cannot move it, the clinic can cancel it, it carries on if the customer is reinstated, and the clinic's home screen counts it. There is no time limit and no disconnect of a single connector. |
